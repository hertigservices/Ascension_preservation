names (`patch-6..9`, `patch-D/E/F/G/H/J/K/L/Y`, `patch-enUS-<c>`), placed to preserve the 38 currently recorded overlap constraints (single-letter Jul-31 "HD" set Q/R/U/V/X/Z

## 3. Addon pack — load order and layers

1. `!AscensionShim` (ours). Implemented layers and later integration targets:
   - `core/Namespaces.lua` — creates `ASC` and an explicit namespace factory. Only implemented API modules opt in. Do not precreate every `C_*` table: pure-Lua modules may guard initialization with `if not C_Name`.
   - `core/EventBus.lua` — the 153 custom events. Hooks `Frame:RegisterEvent`/`UnregisterEvent`
     via the frame metatable: explicitly inventoried custom event names are recorded per frame and dispatched by
     `ASC.Events.Fire(name, ...)` calling the frame's OnEvent script. Stock events pass through
     untouched.
   - `core/Transport.lua` (not implemented) — planned addon-message channel to `mod-ascension-ca`: prefix `ASC`,
     whisper-to-self, `ASC.Send(verb, ...)`, request ids, fragment reassembly
     with request/transfer IDs, bounded reassembly, `HELLO` handshake, mode, connected state. The existing prototype fragment syntax lacks transfer identity and is not sufficient for concurrent state/build responses.
   - `core/Data.lua` — accessors over the generated tables (entries by id/class/tab, edges,
     essence curve, classes, tabs, categories and specializations).
   - `core/BuildData.lua` and optional generated catalogue chunks — preserve complete captured records, source realm/date and spell order; no build activation.
   - `data/*.lua` — generated (never hand-edited).
   - `compat/**` (integrated by `tools/assemble_panel_pack.py`, P2) — Ascension SharedXML/FrameXML
     files copied verbatim in Ascension's own FrameXML.toc order (the MANIFEST in the tool), with
     every `<Script>/<Include>` sibling an XML names, bracketed by ours: `aa_StockPrelude.lua`
     (error capture to the server log, retail-era globals, native stubs, fallback strings,
     class identity + UnitClass wrappers), `SharedXML/C_Hook.lua` (event bus without the
     attribute trampoline that recurses on stock), `zz_AttributeNames.lua` (generated) and
     `zz_StockShim.lua` (widget metatable getters, GetAllAttributes, LoadUI plumbing, class
     name tables, 0.9 UI scale, `/ca`). Two rules the tool enforces: (a) the stock client keeps
     the FIRST definition of a virtual template name and its FrameXML loads first, so every
     colliding non-font template is renamed `ASC_<name>` in the copied compat files AND addons
     (inherits lists and Lua string literals rewritten; `tools/template_collisions.py` lists
     them); (b) a missing template or font only shows in `Logs\FrameXML.log`, never in Lua.
   - `api/*.lua` — currently preview-only `C_ClassInfo`, `C_CharacterAdvancement`, and `C_BuildCreator`; later one adapter per required native namespace (`C_CharacterAdvancement.lua`, …) and
     `api/Globals.lua` for the custom globals. Each function carries a comment with its
     contract (args, returns, which UI call sites use it) taken from the Understand map.
2. Ascension's addons, verbatim (`assemble_panel_pack.py` copies AscensionResources,
   Ascension_Collections, Ascension_TalentUI, Ascension_CoATalents; more per phase). The only
   edits are mechanical and made by the tool at assembly time: the `ASC_` template renames above,
   and a `## Dependencies: !AscensionShim` line where needed (recorded in `client/PATCHES.md`).

Stock FrameXML stays in the MPQ; no loose FrameXML/GlueXML until phase P4 (character
creation). Executable startup corrections also address the bounded archive count and signature caller dispatch; they are separate from custom-class support, which is not implemented yet.

## 4. Data tables

Generated by `tools/gen_ca_data.py` from (authority order): `advancement.tsv` (live API
shape, 10,250 nodes), `entries.json` and class/tab/category exports (DBC columns incl. Description), plus raw essence, specialization and class-identity DBCs. The remaining custom DBCs still need decoding. `gen_build_data.py` separately reads the full community catalogue JSON inside the harvest ZIP. The local `builds.json` plans and original archetype DBCs still require separate reconciliation; the truncated `ca-builds.tsv` is not the catalogue authority. One entry record has the fields the live client returned,
same names (`ID, Name, Class, Tab, Type, NodeType, Quality, RequiredLevel, AECost, TECost,
Spells, Icon, Anchor, Color, Column, Row, PositionX, PositionY, SizeX, SizeY, ConnectedNodes,
Masteries, RequiredIDs, Flags, Group, ParentNode, Points, Required*Investment, isAbility,
isTalent, isMastery`) plus `Description`, `ClassTypeID`, `TabTypeID`, `SpellIDs`.
Split entry chunks per class under `data/datasets/<key>/lua/entries/`, each at most 350,000 bytes. `gen_ca_data.py` writes dataset-specific `world-staging.sql` beside the Lua/JSON outputs. `gen_build_data.py` writes a separate catalogue and SQL. All captured reference records are emitted from the same in-memory model and checked for cross-format parity.

### 4.1 Dataset selection and recoverable gaps (2026-09-09)

The live harvest contains three realm/mode variants, not duplicate interchangeable rows. The generator preserves each `(realm, mode)` dataset independently; it never averages or unions costs and level requirements. Selecting a dataset for an offline preview is explicit and does not establish that its captured costs are correct for CoA gameplay. P3 must validate the selected rules before enabling learns.

`Spells` harvest cells contain JSON records `{id, name}`; the UI consumes ordered numeric spell IDs. Generated `Spells` and `SpellIDs` preserve rank order, while harvested names remain available as `SpellNames`. Blank unknown fields stay absent. Five DBC-only placeholder entries retain evidenced DBC fields and are marked as lacking harvested rules; unknown costs are not inferred from DBC Cost1/2/3.

One generation emits normalized JSON, split Lua chunks, SQL staging tables, and integrity/provenance manifests from the same in-memory records. Datasets have separate composite keys in SQL. SQL is generated only, never applied automatically. Keep unresolved edge targets and opaque `<table>` fields in the gap report; rendering may omit an unavailable relationship, while gameplay must fail closed for rules it cannot establish. Recompute class/tab counts from the selected data rather than forcing the older 42/153 estimate.

## 5. Proposed wire protocol (module <-> shim; not implemented beyond HELLO/PING)

All lines are tab-separated, prefix `ASC`. Client sends `ASC\tCMD\t<verb>[\t<arg>...]` as a
whisper to itself; the server replies as whispers from the player to the player with
`ASC\t<verb>...`. A body longer than 240 bytes is fragmented as
`<verb>\t<seq>\t<count>\t<chunk>` in the existing prototype. Before STATE/BUILD or mutations are added, version the protocol and add request/transfer identity, sender validation, timeouts, byte/fragment limits, duplicate handling and atomic snapshot replacement on both sides. The table below records intended semantic messages, not a complete wire contract.

| Direction | Line | Meaning |
|---|---|---|
| S->C | `HELLO <protocol> <mode> <enabled>` | sent on login and on request |
| C->S | `CMD PING` / S->C `PONG` | liveness |
| C->S | `CMD STATE` | ask for the full character CA state |
| S->C | `CLASS <coaClassByte> <coaClassName> <carrierClass>` | the character's CoA identity |
| S->C | `ESSENCE <ae> <te> <maxAE> <maxTE> <level>` | budgets (family = class byte) |
| S->C | `KNOWN <seq> <count> <id:rank,id:rank,...>` | complete known-entry set (fragmented) |
| C->S | `CMD LEARN <entryId>` / `CMD UNLEARN <entryId>` | one node; server validates, teaches, replies |
| S->C | `RESULT <verb> <ok|ERR_...> [<entryId>] [<message>]` | outcome; on ok the server also re-sends ESSENCE and KNOWN |
| C->S | `CMD SETCLASS <coaClassByte>` | choose the CoA class (first login / archetype) |
| C->S | `CMD BUILD LIST` / `BUILD GET <uuid>` / `BUILD ACTIVATE <uuid>` | Hero Architect |
| S->C | `BUILD <seq> <count> <json-ish>` | build catalogue / detail |
| S->C | `EVENT <name> [<args>]` | fire a custom client event (e.g. `CHARACTER_ADVANCEMENT_LEARN_RESULT`) |

Semantics carried over from the Ascension protocol (measured): the client's known set is
authoritative on unlearn only through explicit UNLEARN; the server never merges, it
replaces; essence family 10 (Free-Pick) vs 28 (Tinker) — never serve the wrong family; a
`(0,0)` budget means "withhold", not zero.

## 6. Server module

Target `mod-ascension-ca`, C++ PlayerScript + WorldScript. The current source under `src-coa2` only implements HELLO/PING and a fragment sender; learning/state tables and the transport client are absent. Planned tables in
the characters DB: `ca_known(guid, entry, rank, learned_at)`, `ca_class(guid, class_byte,
archetype)`; the generated world staging schemas currently contain dataset-keyed `ca_dataset`, `ca_entry`, `ca_spell`, `ca_edge`, `ca_essence`, `ca_reference` and separate `ca_build_catalogue`, `ca_build`, `ca_build_spell`. These drafts have not been applied and are not production migrations. Learn must validate level, prerequisite rules, investment, essence, mode and requested rank, then grant the validated rank spell(s); the ordered `Spells` array must not be blindly treated as a list to teach in full. Unlearn must reconcile remaining dependencies and known spell ownership, rather than removing shared grants indiscriminately. Class identity:
planned stock carrier class server-side (selection still needs validation), with CoA identity represented consistently on both sides. The preview does not override `UnitClass` or modify real player state. P4 must implement and test the selected identity/executable approach.

## 7. Verification ladder (every phase)

1. `tools/luacheck_pack.py` — every `.lua` in the pack compiles (Lua 5.1 syntax via the
   hub's compiler) and every global referenced by the pack resolves to: stock API, stock
   FrameXML, the shim, the pack, or an explicitly whitelisted late-bound name.
2. In-client: `/asc selftest` reports counts, unresolved relationships, incomplete captured rules and event-hook failures. Six missing relationships are documented per dataset; do not fabricate targets to make a check pass. Counts come from the selected generation manifest.
3. Panel opens via `Collections:GoToTab(Collections.Tabs.CharacterAdvancement)`; screenshot.
4. Independent review remains an acceptance task. Current user direction is solo work with no new fan-out or review panels; Claude must review the Codex checkpoint before resuming.
